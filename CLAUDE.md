# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Dots and Boxes" («Крапки й квадрати»): the two-player Dots and Boxes game on an NxN field, in English, Ukrainian, German, French, Italian and Spanish. Players take turns drawing a line between adjacent dots. The first line can go anywhere; every later line must start from an existing one. A player who closes a square owns it, and whoever owns the most squares wins.

Stack: Vue 3 (`<script setup lang="ts">`), Vite, TypeScript, Tailwind CSS v4 (via `@tailwindcss/vite`, imported in `src/assets/styles.css`), vee-validate + `@vee-validate/rules`, vue-router, vue-i18n, `vite-plugin-pwa`, Nunito via `@fontsource-variable/nunito`, Pinia (installed, but `src/stores/counter.ts` is unused scaffold). SCSS is available for `<style lang="scss">`.

## Specs

Specs live in `docs/` (layout and workflow in `docs/README.md`). Domain terms are in the root `GLOSSARY.md` and decisions in `docs/adr/`; use the glossary's terms in code, docs and issues. Shipped behavior is in `docs/<feature>/requirements.md` (numbered rules such as `MV-2`) with `design.md` and the design canvas; new work starts as `docs/<feature>/spec.md`, mirrored to a GitHub issue, and is tracked as GitHub sub-issues (no `tasks.md`). Read the spec before implementing a feature, update the spec first when behavior changes, and reference requirement or story IDs in commits. The gameplay spec is `docs/dots-and-boxes/`.

- `npm run build:capacitor`: the Android app's web build (`vite build --mode capacitor`, base `/`, no PWA plugin)

Needs JDK 21 and `ANDROID_HOME` (the Android SDK). Gradle reads `ANDROID_VERSION_NAME`/`ANDROID_VERSION_CODE` (defaults `1.0.0`/`10000`) and refuses a signed build without both version vars, and signs only when `ANDROID_KEYSTORE_FILE` (plus `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`) is set; otherwise the AAB is unsigned.

Finds the SDK in `ANDROID_HOME`, `~/Library/Android/sdk` or `~/Android/Sdk`. The debug app id ends in `.debug`, so it installs next to the Play Store app. `npm run android:install` also installs it with `adb install -r` on a phone connected over USB with USB debugging on.
- `npm run android:open`: opens `android/` in Android Studio

Tests: specs sit in `__tests__/` folders next to the code (`*.spec.ts`) and check external behavior only (spec "Testing Decisions"). CI: `.github/workflows/ci.yml` runs type-check, `lint-check` and tests on every pull request. Deployment: `.github/workflows/deploy.yml` runs the tests, then publishes to GitHub Pages on every push to `master` that changes the app (its `paths` list, as in teach-clock: `src/`, `public/`, `index.html`, build config, `package*.json`, `scripts/`, the workflow itself). It builds with `BASE_PATH=/<repo name>/` (`/dots-and-boxes/` after the rename), which `vite.config.ts` reads as Vite's `base` and the router picks up through `import.meta.env.BASE_URL`, then copies `dist/index.html` to `404.html` so history-mode reloads work. Keep asset and route URLs base-relative (no hard-coded `/…` paths in code).

Android release: `.github/workflows/android-release.yml` runs, as in teach-clock, on every push to `master` that changes the app (`deploy.yml`'s `paths` list plus `android/**` and `capacitor.config.ts`, so merges of docs, tooling or other workflows release nothing) and on tags `v*.*.*`. A `version` job skips a `master` push whose version is already tagged; after the upload a `master` release tags its commit `vX.Y.Z` (pushed with `GITHUB_TOKEN`, so it starts no second run; needs `contents: write`). Version (AR-11, PV-5): one per commit, raised by every merge to `master`, nothing bumped by hand. `scripts/app-version.ts` gives `MAJOR.MINOR` from `package.json` plus the first-parent merges since `FIRST_RELEASE` (`39683c0`, released by hand as 1.0.0), so `1.0.7` and versionCode `10007` (`10000` + merges). `vite.config.ts` sets `VITE_APP_VERSION` from `appVersion()` (given value, else `ANDROID_VERSION_NAME`, else the commit's own), read as `APP_VERSION` (`src/static/app-version.ts`) and shown on both privacy pages under "Updated". So the web app and an Android build of the same commit show the same version. It needs the whole history: Pages and the Android release check out with `fetch-depth: 0` (a shallow checkout falls back to 1.0.0). To release by hand (e.g. after a docs-only merge), run `npm run release` on a clean, up-to-date `master`: `scripts/release.ts` tags the commit with its own version (`v1.0.7`) and pushes it; it stops when that tag exists (nothing merged since). The job runs `node scripts/app-version.ts`, which prints `ANDROID_VERSION_NAME`/`ANDROID_VERSION_CODE` and, on a tag run (`GITHUB_REF_TYPE=tag`), fails unless the tag is the commit's version, then runs type-check, lint-check and tests, then `build:capacitor`, `cap sync android`, JDK 21, decodes `ANDROID_KEYSTORE_BASE64` to `$RUNNER_TEMP` (passed as `ANDROID_KEYSTORE_FILE`), `gradlew bundleRelease`, attaches the AAB as the `app-release-X.Y.Z` artifact, and uploads it to the Play `alpha` (closed testing) track with `r0adkll/upload-google-play` (`tracks: alpha`, "What's new" files for all six listing languages: `whatsnew-en-US`, `whatsnew-uk`, `whatsnew-de-DE`, `whatsnew-fr-FR`, `whatsnew-it-IT`, `whatsnew-es-ES`; LG-21), `PLAY_SERVICE_ACCOUNT_JSON` and the package from the repository variable `ANDROID_PACKAGE_ID` (checked first, so the job fails early when it's missing). The keystore is deleted in an `if: always()` step. Secrets come from `scripts/android-release-wizard.sh`. The app's first release can't go through the API: upload that AAB by hand (`docs/store/publishing-checklist.md`, step 4). Promoting from closed testing to production stays manual in Play Console.

PWA: `vite-plugin-pwa` in `vite.config.ts` (`autoUpdate`, Workbox precache of all build output, navigation fallback to `index.html`). It emits the first listed language's manifest; a small plugin there adds the other five and `404.html`. File names live in `src/static/manifests.ts`, and `setLocale()` swaps the `<link rel="manifest">` href with the language. Verify with `BASE_PATH=/dots-and-boxes/ npm run build` (all six manifests, `sw.js`, icons in `dist/`), not unit tests. New static assets must match the precache `globPatterns` to work offline. The privacy policy (AR-15, PV-1..PV-4) has one text, `PrivacyContent.vue` with `privacy.*` messages, shown in two places: the in-app `/privacy-policy` route (`src/pages/privacy/`) and the static store page, which `privacyPage()` in `vite.config.ts` renders (Vue SSR of `src/privacy-static.ts` through a throwaway Vite server) to `privacy/index.html` in every build and in dev, all six languages on one page with links to each at the top, with no script, linking the app's stylesheet and the dark theme under `prefers-color-scheme`. Its "Updated" date is the built commit's date: `vite.config.ts` sets `VITE_PRIVACY_UPDATED` (`scripts/privacy-updated.ts`; an existing value wins), read as `PRIVACY_UPDATED` in `src/static/privacy.ts`. Android: Capacitor (`capacitor.config.ts`, app id `app.dotsandboxes`) wraps the capacitor-mode build of `dist/`. ## Architecture

- **App shell** (`src/App.vue`): a header on every screen (logo, translated game name, on Settings only the Home button that returns to Welcome, `ThemeToggle`, the info button that opens the rules panel, `LanguageMenu`), then `RouterView`, then the single `RulesPanel`. Its round icon buttons are `BaseIconButton` (44 px below `sm`, `shrink-0`). The shell is the screen's height (`h-app`: `100vh`, `100dvh` behind `@supports`) and never scrolls (MB-11): every page wraps its content in `src/shared/components/AppScreen.vue`, whose `<main>` is the only scroll area, with a `#footer` slot pinned below it. A new route page must use `AppScreen`, or content past the screen's height is cut off.
- **Routing** (`src/router/index.ts`): `/` (Welcome), `/settings` and `/game` all render the game `Page.vue`, which picks the screen from the route and keeps the address in step with the game (a started game is always at `/game`; `/game` without one goes to `/`); the privacy screen is `/privacy-policy` (name `privacy`); every other path redirects to `/`. Page folders expose their root component through an `index.ts` barrel (`export { default } from './Page.vue'`).
- **Game page flow** (`src/pages/dots-and-boxes/`): `Page.vue` owns a single `reactive(new DotsAndBoxesGame())` and picks the child via `<component :is>` from a computed config (`component`, `props`, `listeners`):
  - A started game (`dotsAndBoxesGame.isGameStarted`: both players plus size > 0) renders `Game.vue`. Otherwise, at `/`, it renders `welcome/Welcome.vue` (WL-1..WL-21): a watch-only how-to-play demo drawn live in inline SVG from the pure `demo-script.ts`, the six steps and Start. Welcome is chosen from the route, with no storage key: `Page.vue`'s `screen` computed shows the game when one is started, Settings at `/settings`, otherwise Welcome. So each launch opens Welcome, a restored game skips it, and the privacy screen returns to the screen it left.
  - After Start it renders `game-setup/GameSetup.vue`. That form has the game mode switch (Versus computer / Two players) and, in computer mode, the difficulty switch, a "You" `PlayerField` and the read-only `ComputerOpponentField`. It emits `gameSetup` from Play, and Page applies the result with the chained setters (`setGameMode(...)` first); its Back emits `back`. Back, the header's Home and Android back all go to Welcome through `backToWelcome()` (`src/router/index.ts`; SP-5..SP-7), which steps back in the browser history when Start opened Settings and replaces the address otherwise, so browser Back from Welcome never reopens Settings.
  - `Game.vue` gets the reactive game as a prop and changes it through model methods. It shows `game/GameBoard.vue` next to `game/GameStatus.vue` (turn, score, Stop) or, once finished, `game/GameResult.vue` (Settings calls `reset()` and leads to Settings, not Welcome; Rematch calls `start()`). The selected dot lives in `Game.vue` and reaches the board through `v-model:selected-dot`.
  - **Footer**: while Welcome or the setup shows, `Page.vue` also renders `src/shared/components/AppFooter.vue` (FT-1..FT-4): Privacy (a `RouterLink` to the in-app privacy screen; the Android back button returns from it to the game) and Contact (`mailto:` with `CONTACT_EMAIL`/`CONTACT_SUBJECT` from `src/static/contact.ts`). The game screen has no footer.
  - **Computer turn**: `Game.vue` uses `useComputerTurn.ts`, which watches `isComputerTurn` (immediate, so a restored game resumes), waits `COMPUTER_DELAY_MS` and draws `chooseComputerLine(...)` through the normal `drawLine`. Its `isThinking` locks the board and shows "Thinking…"; call `cancel()` on Stop, Rematch and Settings.
  - **Rules panel**: the header's info button (`App.vue`) opens `src/shared/components/RulesPanel.vue`, a modal side panel rendered once in `App.vue` around `GameRules.vue`, which renders the same `HowToPlay.vue` block as Welcome (demo plus six steps, stacked) (both are app shell, so they live in `shared/`; full screen below `sm`, closed by default, ✕/backdrop/Esc, focus trapped and returned to the info button). No screen shows rules inline. Its open state is the module-level `useRulesPanel()` composable (`src/shared/composables/`); `Game.vue` passes it to `useComputerTurn` as a pause reason next to the Stop dialog (VR-31). The steps (`welcome.captions`) must match the spec (RL-5).
- **Native (Android) touches** (`src/native/`): `main.ts` imports `@capacitor/core` and it dynamically, only when `__CAPACITOR_BUILD__` (a compile-time flag `vite.config.ts` defines from the build mode, declared in `env.d.ts`) is true and `Capacitor.isNativePlatform()`, so the web build contains no Capacitor code (check `dist/assets` after a Pages build). Each plugin call catches its own failure, so one failing call doesn't stop the others. It handles the back button (language menu, rules panel, then the Stop dialog via the module-level `useStopDialog()`, then the privacy screen back to the game, then Settings back to Welcome (SP-7), then `App.exitApp()`; AR-3) and paints the status bar from `--wc-paper` as the theme changes (AR-4). At launch it asks Google Play for an update (`@capawesome/capacitor-app-update`, `app-update.ts`; AR-20): Play's own flexible prompt, and once downloaded `completeFlexibleUpdate()` installs it and restarts the app (the game is restored from storage). Only Play-installed builds see updates. Android 15+ is edge-to-edge and ignores the background, so the page runs under the system bars (`viewport-fit=cover` in `index.html`): give the app shell and every full-screen `fixed` layer `p-safe-N` (padding N plus the safe-area insets, `styles.css`) instead of `p-N`. Specs fake the Capacitor plugins with `vi.mock` and call `startNative()` after mounting. Icon and splash sources live in `assets/`, written by `npm run generate-icons`; `npm run android:assets` turns them into Android resources (AR-5). The launch splash on Android 11 and older (launch theme background and the `SplashScreen` plugin's `androidSplashResourceName`) is `drawable/launch_splash.xml`, cream plus the `splash_icon.png` logo (also from `generate-icons`) drawn unscaled; never point them back at the full-screen `splash.png`, which Android stretches into ovals (`scripts/__tests__/android-splash.spec.ts`).
- **Persistence**: `Game.vue` writes the whole game to localStorage under `CURRENT_GAME` (`src/static/storage-keys.ts`) in a `watchEffect`, going through `StorageService` (`src/services/storage.service.ts`, which JSON-serializes objects). On load, `Page.vue` reads it back with `getItem(key, { applyParse: true })` and rehydrates it via `dotsAndBoxesGame.reset(savedGame)`. `GameSetup.vue` also saves `GAME_MODE` and `DIFFICULTY` when a game starts and reads them when setup opens. `useTheme` saves `THEME`.
- **Models** (`src/models/`): `DotsAndBoxesGame`, `Dot`, `Line` and `Square` are classes. Each has a `Partial<Self>` constructor that doubles as the JSON rehydrator: it builds nested `Line`/`Dot`/`Square` instances and defaults with `??`, so 0-based `row`/`col` survive. Chainable `setX()` setters return `this`. `reset(game?)` does `Object.assign(this, new DotsAndBoxesGame(game))`, which keeps the same reactive object identity. When adding fields, update the constructor so that restoring from storage keeps working.
  - Game rules live on `DotsAndBoxesGame` (`isValidStartDot`, `validNeighbors`, `canDraw`, `drawLine`, `stop`, `start`, `winner`). `lines` is the single source of truth for drawn edges, and `dirtySquares` holds only owned squares.
  - `gameMode` (`'twoPlayers' | 'computer'`, missing in old saves → Two players) and `difficulty` (`'easy' | 'normal'`, only in computer mode) live on the game; `isComputerTurn` and `legalMoves()` serve the computer player.
  - Ownership is tracked by player **name** (`ownerName`, `getPlayerByName`), so player names must be unique. The setup form enforces this case-insensitively through a custom `differentFromAll` rule.
  - The computer player is always `player2`, stored under `COMPUTER_NAME` (`computer-player.model.ts`) and never shown: display any player name through `useDisplayName()` (`src/shared/composables/`) or `PlayerName.vue` (adds `RobotIcon`). Its color comes from `computerColorFor()` in `src/utils/computer-color.ts`: the swatch most different from the person's color.
  - `computer-strategy.ts`: `chooseComputerLine(game, difficulty, random)` is pure (Easy: random legal move; Normal: claim, else safe line, else fewest given away). Test it with a fixed random source.
- **i18n** (`src/i18n/`): vue-i18n with the Composition API (`legacy: false`). `languages.ts` holds the one ordered list (code, key, own name) that drives messages (`messages.ts`), the menu, detection, the first-paint script the build injects (`first-paint.ts`, LG-8), manifests, the privacy page and test loops. `locales/en.ts` defines the message keys, and every other locale is typed as `typeof en`, so all must have the same keys. With no saved `LOCALE` the first launch uses the first `navigator.languages` entry on the list, otherwise `en` (LG-6, AR-6), and a saved `LOCALE` always wins; `setLocale()` saves `LOCALE` in localStorage and updates `<html lang>`, `document.title` and the `<link rel="manifest">` href (one manifest per language, `src/static/manifests.ts`). All UI text goes through `const { t } = useI18n()`; never hard-code visible strings, and add every new string to all six locale files. The app names live in `app.*` and in Android's `values*/strings.xml`. vee-validate messages come from `configure({ generateMessage })` in `src/i18n/index.ts`, using each `<Field>`'s translated `label`. The language button (one round `BaseIconButton` showing the current key, opening a menu of the list; LG-1..LG-4) is `src/shared/components/LanguageMenu.vue` in the `App.vue` header.
- **Theme and styling** (`src/assets/styles.css`): the Warm cream palette is `--wc-*` custom properties, light on `:root` and dark on `:root[data-theme='dark']`, exposed to Tailwind through `@theme inline` as semantic colors (`bg-paper`, `bg-surface`, `text-ink`, `text-ink-soft`, `text-muted`, `bg-accent`, `text-on-accent`, `border-border`, `bg-dot`, `text-danger`, …). Use these tokens, never raw `gray`/`blue`/`white`, so both themes work. `useTheme()` (`src/shared/composables/useTheme.ts`) follows `prefers-color-scheme` live until `toggle()` saves an override under `THEME`, and sets `data-theme` on `<html>`; an inline script in `index.html` applies the same rule before the app loads. Old Android WebViews (AR-21, floor `OLDEST_CHROME` = Chrome 88 in `src/static/oldest-chrome.ts`): `oldWebViewCss()` in `vite.config.ts` flattens Tailwind's `@layer` and fixes its `var(--x,)` fallbacks in the built CSS; in app code use no `color-mix()` (use `tint()` from `@/utils`), no opacity modifier on a theme color (`bg-ink/40` falls back to opaque; add an alpha-hex token like `bg-backdrop`/`bg-accent-tint`), and `transform` instead of the `scale`/`translate` utilities. `scripts/__tests__/css-floor.spec.ts` builds the Android CSS and enforces this.
- **Player colors**: `SWATCHES` in `src/utils/swatches.ts` (8 key + hex pairs, keys double as `colors.<key>` i18n keys) and `randomSwatch(except?)`. `PlayerField.vue` renders them as a radiogroup bound to the same `player.color` hex, with a `differentColor` rule in Two players mode. Saved games may hold any hex, so never assume a color is a swatch.
- **Logo and icons**: `src/shared/logo.ts` (`logoSvg()`, `faviconSvg()`) is the one SVG source; `AppLogo.vue` renders it in the header with `currentColor` dots and an animation that respects reduced motion. `npm run generate-icons` (`scripts/generate-icons.ts`) regenerates `public/favicon.*` and the install PNGs after a logo change; commit them. UI icons are inline SVG components in `src/shared/icons/` (Material Symbols Rounded, license in its README); no icon font.
- **Forms**: vee-validate `<Form>`/`<Field>` with string rules (`required|min_value:2|max_value:10`). Rules are registered with `defineRule` inside the component that uses them. Nested field names like `player1.name` map onto the `GameSetupForm` shape.
- **Shared UI** (`src/shared/components/Base*.vue`): Tailwind-styled primitives, including `BaseSegmentedControl` (radiogroup switch for game mode and difficulty). `BaseInput` forwards `$attrs` so it can take vee-validate's `field` binding.
- **Imports**: use the `@/` alias for `src/`. `models`, `services`, `static` and `utils` each have an `index.ts` barrel.

## Conventions

- TS is strict with `noUncheckedIndexedAccess` enabled, so indexed access returns `T | undefined`.
- Linting: oxlint `correctness` category is set to error, and ESLint uses `vue/flat/essential` plus the vue-ts recommended config. Prettier owns formatting (`eslint-config-prettier`).
- Node `^22.18.0 || >=24.12.0`.
- **Design and store images (last step of every feature)**: when a feature or spec's work is done and anything visible changed (UI updates or a new visible feature), sync three things before the PR is marked ready, on the feature's branch: (1) the local boards in `docs/dots-and-boxes/design-canvas/*.dc.html` (plus the matching text in `design.md`), (2) the remote canvas linked in `docs/dots-and-boxes/design.md`, and (3) the store images (`npm run store:screenshots`, then review and commit them). The remote canvas is a claude.ai artifact that embeds every board: its `<script id="appifact-doc">` JSON holds `content.files` (`<name>.dc.html` and `canvas.json`), so read it with the Artifact tool, replace that record with the local files and republish to the same URL. This is `docs/README.md` workflow step 5; `/implement-spec` and similar flows don't do it on their own.
